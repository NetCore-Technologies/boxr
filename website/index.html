01 / THE IDEA

Small on purpose.
Clear by design.

boxr focuses on the mechanics that make a container feel like its own little machine: process IDs, host identity, mount tables, IPC, and resource limits.

No daemon to keep alive. No giant stack to understand before you can read the code. Just a compact Go project that lets you inspect the moving parts.

03 / THE WORKFLOW

One command.
Know what it does.

Run a process with separate kernel namespaces, an optional root filesystem, persistent OverlayFS writable layers, safe JSON recipe image builds, local OCI-layout images with integrity checks and Boxr-format registry pull/push, named volumes, explicit mounts, capability controls, an optional baseline seccomp denylist, redacted dry-run planning, rootfs/image security audits and cgroup resource ceilings. No background daemon required.

A NOTE ON SECURITY

Isolation primitives are
not a security boundary.

Boxr now supports optional chroot rootfs isolation, persistent OverlayFS writable layers, private user and loopback-only network namespaces, read-only rootfs and bind mounts, named persistent volumes, single-layer OCI-layout image storage with verified OCI Distribution pull/push for Boxr images, capability drops, no-new-privileges, and an optional fixed seccomp baseline denylist. Arbitrary multi-layer Docker/OCI image application remains unsupported. It still has no configurable seccomp allowlist, device filter, LSM policy, veth/bridge/NAT networking, or hardened multi-tenant threat model. Without --rootfs, the host filesystem remains visible. Do not run untrusted workloads.
