# Docker Engine API compatibility

Boxr includes an initial, intentionally limited Docker Engine HTTP API for local tooling. It exposes runtime-backed read operations plus a narrow set of safe container lifecycle mutations; unsupported operations fail explicitly. Start the daemon:

```sh
boxr daemon
```

By default it listens on `$XDG_RUNTIME_DIR/boxr/engine.sock`, or `~/.cache/boxr/run/engine.sock` when `XDG_RUNTIME_DIR` is unset. Override the path with `--host unix:///absolute/path/engine.sock`. The socket is owner-only (`0600`); the daemon refuses symlinked socket paths, unsafe socket directories, replacement of regular files, and a second live listener. For remote administration, one TCP listener is available only with mutual TLS: plaintext TCP is rejected, the server verifies client certificates against the configured CA, TLS 1.2 or newer is required, and the server private key must be owner-only.

Engine API-created containers now unpack the verified image into a private, container-owned immutable rootfs snapshot at create time. That lower snapshot is retained with the container until it is removed or pruned, even if the original local image tag is later deleted. The persistent OverlayFS writable layer is mounted over the snapshot on each start. Native CLI workloads continue to use the explicitly configured `--rootfs` policy.

Engine API-created containers are assigned a dedicated cgroup v2 child before their startup barrier opens, even when no resource limits are initially configured. This makes later Docker Engine `/containers/{id}/update` calls safe to apply without migrating a live process out of the Boxr parent cgroup. Engine API-created containers also receive a private per-container OverlayFS writable layer under the Boxr state directory. The layer is reused when a stopped container starts again, keeping filesystem changes separate from the verified image rootfs, and is removed with the container record. This persistence is limited to Engine API-created containers; native CLI workloads continue to use the explicitly configured `--overlay-dir` policy.

A Docker CLI can use that socket for the implemented operations shown below; most container lifecycle and image workflows still require native Boxr commands:

```sh
export DOCKER_HOST=unix:///absolute/path/engine.sock
docker version
docker info
docker ps --all
docker images
docker inspect CONTAINER
docker logs CONTAINER
docker stats --no-stream CONTAINER
```

For a remote Engine API listener, provision a CA, a server certificate whose SAN matches the daemon hostname/IP, and client certificates signed by that CA. Start Boxr with:

```sh
boxr daemon \
  --host tcp://0.0.0.0:2376 \
  --tlsverify \
  --tlscacert /etc/boxr/ca.pem \
  --tlscert /etc/boxr/server-cert.pem \
  --tlskey /etc/boxr/server-key.pem
```

Connect from a Docker-compatible client with its own client certificate and the CA:

```sh
docker --host tcp://boxr.example.com:2376 --tlsverify \
  --tlscacert ca.pem --tlscert cert.pem --tlskey key.pem version
```

Every client certificate trusted by the configured CA receives the full Engine API authority; there is no per-client role model yet. Treat client private keys as privileged host-administration credentials. Only one listener (Unix or mutually authenticated TCP) can be configured per daemon process.

The container attach endpoint supports Docker's `logs`, `stream`, `stdin`, `stdout` and `stderr` query switches and uses the same bounded log snapshot/follow path as the logs endpoint. With `Connection: Upgrade` and `Upgrade: tcp`, it returns `101 UPGRADED` and streams Docker multiplex frames over the hijacked connection; the same bidirectional connection forwards raw stdin bytes when `stdin=1` is requested. Stdin requires a container created with `OpenStdin=true`; `StdinOnce=true` closes the workload's stdin after the first attached client disconnects, while `StdinOnce=false` permits a later attach session to continue sending input. TTY container creation remains unsupported, so attached stdin is a non-TTY raw byte stream. Without upgrade headers, attach remains a normal HTTP stream for output-only clients. Since Boxr's supervisor persists stdout and stderr into one combined log, that combined stream is framed on stdout (or stderr when requested alone); log truncation resets the follow offset so a rotated log can be read from its new beginning. Exec sessions use Boxr's namespace-aware executor. On Linux, TTY sessions allocate a real pseudo-terminal, accept stdin over Docker's `Connection: Upgrade` / `Upgrade: tcp` hijacked stream, merge stdout and stderr into the raw terminal stream, and support `POST /exec/{id}/resize?h=HEIGHT&w=WIDTH`; non-TTY sessions preserve Docker's 8-byte multiplexed stdout/stderr frames. Attached stdin requires the upgraded bidirectional stream, and `Privileged` exec and custom detach-key sequences remain unsupported. The image-create endpoint accepts Docker's `X-Registry-Auth` header or configured Docker/Podman auth files; it verifies the registry manifest, every layer digest and each uncompressed DiffID before importing into the local OCI store. The default platform is the host Linux architecture; callers may set `platform=linux/ARCH[/VARIANT]`. Immutable pulls accept `fromImage=registry/repository@sha256:...` or a `tag=sha256:...` selector. Boxr verifies the requested manifest digest and maps the immutable reference to a deterministic local tag (`repository:sha256-HEX`) so the image remains addressable in its tag-oriented local store; native create requests accept the digest reference and resolve it to the same alias. Image export uses Docker-save format; image load validates all archive tags and refuses to overwrite any tag persisted by a container. Imported multi-layer Docker images are flattened into Boxr's native single-rootfs-layer representation. The image-prune endpoint defaults to `dangling=true`; Boxr's store indexes named tags only, so the default leaves tagged images intact while reclaiming any already-orphaned blobs. `dangling=false` selects unused tags and supports Docker-compatible `until`, `label` and `label!` filters. If a persisted container references an image digest, all aliases for that digest are retained. Selected tags are removed with one atomic OCI index update, then unreferenced manifest/config/layer blobs are deleted and reported through `ImagesDeleted` and `SpaceReclaimed.\n\nThe image history endpoint reflects Boxr's image-store model: each image is persisted as one flattened rootfs layer, so the response contains one snapshot entry and explicitly states that original Docker instruction history was not preserved. It does not invent per-instruction records.

The container export endpoint returns an uncompressed tar archive of the merged image and writable-layer filesystem. For running or paused containers it reads through the verified process root; for stopped containers it merges the managed lower and upper layers. It uses the same 8 GiB/100,000-entry archive bounds as commit and excludes bind mounts, tmpfs mounts and image-declared volumes.

The commit endpoint accepts Docker's `container`, optional `repo`/`tag`, `author`, `comment`, and `pause` query parameters plus an optional image-config JSON body. It snapshots only stopped, image-backed Engine API containers with Boxr-managed lower and writable layers; running containers are rejected rather than copied inconsistently. The merged rootfs snapshot is bounded to 8 GiB and 100,000 entries, is validated through the rootfs archive extractor, and becomes a new local OCI image. Bind mounts, tmpfs mounts and image-declared volumes are excluded while empty mountpoints and the effective command/environment/runtime defaults are retained. Referenced tags cannot be overwritten. Docker's `changes` instruction list and live-container pause/snapshot behavior are not implemented; stop the container first and use a Dockerfile build for filesystem/config changes that need explicit instructions.

The build endpoint accepts a bounded tar context (maximum 8 GiB), one or more t tags, a relative Dockerfile path, a platform and JSON build arguments. It uses the supported single-stage Dockerfile subset documented in docs/dockerfile-build.md; build tags referenced by persisted containers are protected from replacement. Pull progress and errors are streamed as JSON records. Container create can then consume the pulled tag. The start endpoint accepts created, exited and failed Engine API containers; an explicit start clears an earlier manual-stop marker before launching the saved image and configuration. Image push exports a verified local image and publishes it with the same Docker auth header or configured auth file; the current Boxr image store exports a single canonical rootfs layer, so the API does not preserve original multi-layer build history. Container list and inspect responses expose verified IPv4 bridge network IDs, addresses, gateways, prefix lengths, stable endpoint IDs and configured MAC addresses from Boxr's managed IPAM leases. Docker network create/inspect also preserves a bounded IPv4 IPAM allocation range. Network inspect reports the same endpoint IDs and MAC addresses. Docker network DNS/service discovery and IPv6 addressing are not yet implemented. The `/containers/{id}/changes` endpoint compares the immutable image snapshot with the Engine API container's OverlayFS upper layer, including OverlayFS whiteouts and opaque directories; it returns Docker change kinds (`0` changed, `1` added, `2` deleted). It is available only for Engine API containers whose rootfs and writable layer are managed by Boxr, and bounds directory entries, traversal depth and path sizes. The `/containers/{id}/archive` GET/HEAD/PUT endpoints provide the core `docker cp` archive transport for managed Engine API containers. GET returns a merged view of the immutable image snapshot and OverlayFS upper layer (or the verified live container root), emits an uncompressed tar stream and Docker's `X-Docker-Container-Path-Stat` header with an RFC 3339 modification time, and refuses special files. Paths may be relative to the container root or absolute; a trailing `/.` copies only the selected directory's contents. Container symlinks in the requested path are resolved with a 40-hop limit and confinement to the container root. PUT validates the entire tar into a private staging directory before applying it to the managed upper layer for stopped containers or the verified live container root for running/paused containers; archive paths, links, entry counts and expanded bytes are bounded. Uploads reject device nodes and OverlayFS whiteout names, strip setuid/setgid bits, and do not apply archive ownership. `noOverwriteDirNonDir=true` rejects directory/non-directory type replacement, while `copyUIDGID=true` is rejected rather than silently ignored. Live archive operations reject `/proc`, `/sys` and `/dev` paths and require a verified container process. The endpoint refuses unmanaged container filesystems. The `/containers/prune` endpoint removes Boxr state records, Engine API sidecars and logs through the native state-store safeguards. `SpaceReclaimed` is currently reported as zero because Boxr does not yet account for per-container writable filesystem layers; caller-managed rootfs and OverlayFS directories are not deleted by prune. Multiple `label!` expressions follow Docker's combined-exclusion behaviour: a container is protected from pruning only when it matches every negative-label expression. Pause and unpause require a verified process in the container's dedicated cgroup v2 subtree. Paused containers remain active for listing, wait, stop, kill, and removal checks; stop/kill resume them before signal delivery, and prune never treats them as stopped.

Stats and live resource updates require a Linux cgroup v2 container with the relevant controllers delegated to Boxr. Live updates verify the recorded PID start time and Boxr container identity before touching the cgroup, validate every target control before writing, and roll back partial kernel writes or failed state persistence. The update endpoint intentionally rejects unsupported Docker resource fields rather than silently ignoring them. Unsupported API versions and unsupported methods are rejected.

**This is not a Docker Engine replacement yet.** Container create/start/stop are implemented only for a strict supported subset: create requires a verified local image, privileged mode, devices, capability additions and unsupported HostConfig fields are rejected. Docker TTY containers run under a controlling PTY with merged stdout/stderr; stdin attachment is available only when `OpenStdin=true`. Stop timeouts are bounded (including a five-minute cap for `t=-1`). Explicit start and restart are supported through the saved image/configuration and native detached supervisor. Restart sends a graceful stop first, escalates to SIGKILL after the requested bounded timeout, and refuses containers configured for automatic removal. BuildKit and remote-context image builds, unsupported structured mount options, network aliases, links and custom network driver options, Docker plugins, swarm and TCP listeners are not implemented by this API layer. The `/build` endpoint accepts `networkmode=none` or `host`; Docker's `default` is mapped to Boxr's isolated `none` mode, while host networking remains opt-in. Base images must already exist in the local image store. The endpoint rejects `pull=true`, `nocache=true`, `rm=false`, remote contexts, BuildKit sessions, multi-stage builds and unsupported query parameters. Temporary context and build state are always removed. Dockerfile `RUN` steps execute with Boxr's namespace, capability-drop, no-new-privileges and baseline seccomp controls.\n\nContainer create honours `Config.Entrypoint` overrides (including an explicit empty array to clear the image entrypoint) and `Config.Cmd` overrides. Image and create-request `Config.ExposedPorts` are merged and retained in image/container inspect metadata; declaring a port does not publish it on the host. Image Dockerfile `STOPSIGNAL` and create-request `Config.StopSignal` are validated, persisted and used by graceful stop before the SIGKILL fallback. It also creates anonymous persistent volumes for image or create-request `Config.Volumes` declarations, while explicit mounts at the same target take precedence. Dockerfile `VOLUME` declarations and image config metadata are preserved through local image builds, OCI storage, Docker-save export/import and image inspect. It also mounts pre-created Boxr named or anonymous volumes through Docker's `HostConfig.Binds` short syntax (`volume-name:/container/path[:ro|rw]`) and accepts a strict subset of `HostConfig.Mounts`. Structured bind mounts require an existing non-symlink absolute host path; only the default `rprivate` propagation is accepted, and host mountpoint creation and recursive mount flags are rejected. Structured volume mounts require an existing local Boxr volume. By default, Boxr copies the image directory into an empty volume during create; set `VolumeOptions.NoCopy=true` to suppress this. Copy-up is skipped for non-empty volumes and refused while another Boxr container is actively using the volume. File contents, directory structure and normal permission bits are copied through a bounded no-follow tree walk; symlink targets are preserved exactly and never followed, while special files are rejected. Ownership and setuid/setgid bits are not preserved. Structured tmpfs mounts require an explicit positive `SizeBytes` (up to 1 GiB per mount and 2 GiB total) and support `Mode`; custom `TmpfsOptions.Options` and read-only tmpfs are rejected. Duplicate and nested mount targets are rejected to avoid order-dependent mount overlays. `POST /volumes/create` creates an anonymous volume when `Name` is omitted. Docker restart policies remain separate from the manually requested restart endpoint. The wait endpoint supports Docker's `not-running`, `next-exit`, and `removed` conditions. `next-exit` snapshots the last persisted finish time and waits for a subsequent start/finish cycle rather than returning a historical exit; `removed` observes deletion and returns the last recorded exit code (zero for a never-started container). All wait conditions stop promptly when the HTTP request is cancelled. Image delete removes a tag from the OCI index; content-addressed blobs remain eligible for the separate Boxr prune operation rather than being deleted during the API request. Kill signals and removal of created/stopped containers are also implemented. Volume prune removes unreferenced anonymous volumes by default; `all=true` includes named volumes, and persisted container references are protected. The volume API supports only the local driver; driver options and third-party volume plugins are rejected. The network API supports only Boxr-managed IPv4 bridge networks. Custom drivers, IPv6, internal/ingress networks are unsupported. Docker IPAM `IPRange` and `AuxiliaryAddresses` are validated, persisted and returned by inspect; auxiliary addresses are excluded from automatic allocation and rejected as static endpoint addresses. Connect/disconnect only attach verified running containers started with network mode `none`. Connect accepts Docker `EndpointConfig.IPAMConfig.IPv4Address` and a validated unicast `EndpointConfig.MacAddress`; requested addresses must be usable, in-subnet and unallocated, while MAC values are persisted and configured on the container interface. New managed attachments receive a stable endpoint ID and a generated locally administered unicast MAC when no override is supplied. Network aliases, links, IPv6/link-local addresses and driver options remain unsupported. Network prune skips bridges with leases or persisted container references. Volume deletion is blocked while any persisted container record references the volume, including stopped and created containers. Container deletion with Docker's `v=1` flag removes attached anonymous volumes after the container is gone, but retains named volumes and anonymous volumes still referenced by another container. Forced removal reuses the native bounded SIGKILL and restart-cancellation logic. Container list and inspect support Docker's `size=1` byte counters (`SizeRw` and `SizeRootFs`), measured from the Boxr writable upper layer and base rootfs with a bounded no-follow directory walk. Container listing supports Docker `status`, `name`, `id`, `label`, `label!`, `exited`, `health`, `network`, `ancestor`, `before`, `since`, `volume`, `publish` and `expose` filters using the stored container image references, volume metadata, declared ports and published port mappings. Ancestor matching is exact to Boxr's flattened image reference/digest; it does not imply parent-image ancestry. The CLI's read commands are not evidence of full Docker CLI compatibility. Boxr's native CLI remains available for creating and controlling containers. Container TTYs currently start at 24x80; dynamic container resize is not yet implemented. Exec sessions support non-TTY multiplexed stdout/stderr streams and Linux TTY/PTY sessions, including upgraded stdin attachment and console resizing. Docker's `Detach` option is accepted on `/exec/{id}/start`, not on exec creation. Privileged exec and custom detach-key sequences remain explicitly unsupported; exec supports Docker's USER override and otherwise inherits the container image/configured user. Session state is kept in daemon memory and is lost when the daemon restarts. Commands launch through Boxr's native exec command, which rechecks container process identity and enters its namespaces and resource cgroup. The server does not expose an unauthenticated TCP endpoint.

Boxr exposes a secure local control socket and a deliberately strict compatibility boundary. It remains a Docker Engine API subset; workloads requiring unsupported operations still require Docker Engine.


Container healthcheck configuration is inherited from image metadata unless overridden by create-request `Healthcheck`. Running probes update the bounded five-entry `State.Health.Log`, status, and failing streak. Probe scheduling is suspended while the cgroup is paused; probes overlapping a pause/unpause interval are discarded rather than counted as health failures.
